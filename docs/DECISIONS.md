# なぜそうしたかの記録

決めたことと、その理由。**後から「なんでこうなってるの？」と思ったらここを見る。**

## 2026-09-01

### 対象範囲は `route-map-2026-04.pdf` の全路線。ただし段階的に進める

最終目標は路線図に載っている全路線・全駅（駅名の抽出結果で1,863件）。
ただし一度に作ると精度が落ちるので、まず地下鉄13路線でアプリまで通し、
動く形を確認してから残りを足していく。

### 駅の並び順は「駅ナンバリングの01側」を起点にする

CLAUDE.md の当初の定義は「路線名の頭側／公式の1番側」だったが、
これは路線によって解釈が割れる（銀座線の起点は浅草か渋谷か）。

駅ナンバリングは事業者が公式に振っている一意の番号なので、
**01側を先頭にする**と決めれば議論の余地がなくなる。

そのため駅ナンバリングをフェーズ2ではなく**フェーズ1に前倒しした**。
路線を1本調べるときに順序と番号を同じページから同時に取れるので、
後から167路線を調べ直すより圧倒的に手戻りが少ない。

ナンバリングが無い路線に限り、従来どおり公式の1番側を起点とし、
`source` に判断根拠のURLを書く。

### 出典は「事業者公式サイト」を最優先、Wikipediaは裏取りに使う

作業中、Wikipedia記事から抽出したふりがなに**6件の誤り**が見つかった
（妙典「みょうてん」、原木中山「はらきなかやま」、白金高輪「しろかねたかわら」、
志茂「しげ」、地下鉄成増「ちかてつなりまし」、小竹向原「こたけむこうはら」）。

そこで**ふりがなは事業者公式のローマ字表記から起こす**ことにした。
ローマ字は読みを一意に定めるので、漢字だけを見て推測するより確実。

- Myoden → みょうでん
- Baraki-nakayama → ばらきなかやま
- Shirokane-takanawa → しろかねたかなわ

Wikipediaは路線カラーや正式路線名の**裏取り**には使う（公式と一致すれば信頼できる）。

### 駅idは事業者公式のローマ字をそのまま小文字化する

自分でヘボン式に変換すると揺れる（新橋を shimbashi にするか shinbashi にするか）。
公式表記に従えば根拠が明確で、再現もできる。

- `Nihombashi` → `nihombashi`（撥音のb前は m のまま）
- `Toranomon Hills` → `toranomon-hills`（空白はハイフン）
- `Meiji-jingumae <Harajuku>` → `meiji-jingumae`（副称は落とす）

CLAUDE.md の例（`nishi-nippori`）もこの方式で再現できることを確認した。

### 副称は `name` に含めず `subName` / `subKana` に分ける

「明治神宮前〈原宿〉」は表示用の結合であって駅名そのものではない。
分けておけば、UIでは結合して出し、検索では両方をヒットさせられる。
逆に結合したまま持つと、「原宿」で検索したときにJR原宿駅と区別できなくなる。

### 数字は半角に統一する

路線図の中で「羽田空港第１・第２ターミナル」（全角）と
「羽田空港第2ターミナル」（半角）が混在していた。
寄せないと検索が破綻するため、**半角**に統一する。

### 支線は別ファイルにする

`stations[]` は一本道の配列なので分岐が表現できない。
丸ノ内線の中野坂上〜方南町は `tokyo-metro--marunouchi-branch.json` に分け、
分岐駅の中野坂上を両方のファイルに入れた。
これで validate.mjs の「乗換駅」判定が正しく効き、
機能③（駅から路線を引く）でも中野坂上から両方に辿れる。

千代田線の綾瀬〜北綾瀬は C19→C20 と連番の一本道なので分けていない。

### 路線カラーは marorika のページの値に統一した（利用者の指示）

当初は事業者公表値を使う方針だったが、利用者の指示により
<https://www.marorika.com/entry/tokyo-metro-line-color-code> の掲載値に統一した。

**浅草線と新宿線は、路線図凡例から実測した色と系統がずれている**（色相差 33°/32°）。
浅草線は本来ローズ（ピンク系）だが採用値は赤橙、
新宿線は本来リーフ（緑）だが採用値は黄緑〜オリーブになる。
指示に従って採用したうえで、生成スクリプトに `USE_MARORIKA` フラグを置き、
`False` にすれば事業者公表値に戻せるようにしてある。
`colorName`（オレンジ／ローズ など）は事業者の公表名のままにした。

なお凡例JPGから画素を拾う方法は採らない。JPEG圧縮で色が濁るため
（銀座線で 実測 `#EFA734` / 公表 `#FF9500`）、色の系統を確かめる用途にとどめる。

### 麹町 は東京メトロ公式の字体（新字体）を採用

- 東京メトロ公式：麹町（U+9EB9）← 採用
- 路線図PDF：麴町（U+9EB4・旧字体）

上記「事業者公式を最優先」の原則に従った。
ただし `refs/map-station-names.txt` との照合では、216駅中これだけが外れる。
麹と麴は別字なのでUnicode正規化では吸収されない。照合スクリプトでは明示的に読み替えること。

### アプリは「テンプレ＋データ → 単体HTML」の形にした

`app/index.html` から `data/*.json` を fetch すると、file:// で開いたときに
CORSで読めない。ダブルクリックで動かせることを優先し、
`tools/build-app.mjs` でデータを埋め込んだHTML1枚を生成する形にした。

UIのソースは `tools/app-template.html`。`app/index.html` は生成物なので直接編集しない。

### 駅名は漢字とひらがなを必ず並べて出す

子どもが漢字を読めなくても使えることが要件なので、
一覧でも詳細でも「ひらがなを上、漢字を下」に必ず2行で出す。
ルビ（`<ruby>`）は文字が小さくなりすぎるので使わない。

### validate.mjs に検査を追加した

駅ナンバリングと副称をデータに持たせたので、それを検査できるようにした。

- 駅番号の形式（`^[A-Za-z]{1,3}[0-9]{2}$`）と路線内での重複
- 路線記号の形式
- `subName` と `subKana` の片側だけの記入
- 駅名に全角数字が混ざっていないか
- 駅番号の記号が路線記号と違う場合は**警告どまり**
  （分岐線ファイルに本線側の中野坂上 M06 が入るのは正常なため）

### 都営4路線を追加したときに決めたこと（同日）

**駅マスタは字体の違いを越えて統合する。**
市ケ谷（JR・東京メトロ）と 市ヶ谷（都営）は物理的に同じ駅なので `ichigaya` の1エントリにした。
CLAUDE.md の「名前が違えば別駅」は 船橋／京成船橋 のような別名を指すのであって、
同じ名前の字体違いまで分けると乗換駅として繋がらなくなる。
採用したのは 市ケ谷（路線図PDFもこちら）。

**小川町は先回りして id を修飾した。**
都営新宿線の小川町を `ogawamachi-tokyo` にした。
東武東上線にも小川町があり路線図にも載っているので、
後から片方を改名するより最初から分けたほうが手戻りが無い。

**大江戸線の環状部は一本道として持つ。**
E01→E38 の順に並べると隣り合う駅同士は実際に隣接しており、配列として破綻しない。
ただし環状部を閉じる「都庁前(E28)〜新宿西口(E01)」の1本だけは表現できていない。
これを持つために `stations[]` をグラフ構造に変えるのは、
残り150路線のほぼ全てにとって過剰なので採らなかった。UI側で補う。

**都営のカラーコードは第三者出典＋凡例実測の二段構えで決めた。**
東京都交通局の公式サイトは本文が取得できず、Wikipediaにもカラーコードが無かった。
colordic.org の掲載値を採り、路線図凡例JPGから拾った実測値と色相が一致することを確認した。
公式資料で裏が取れていないことは `docs/LINE_CHECKLIST.md` に明記してある。

**抽出した駅名リストは NFC 正規化する。**
路線図PDFは 蓮（蓮根・本蓮沼）を CJK互換漢字 U+F999 で組んでいた。
そのままだと通常の 蓮（U+84EE）と文字列一致しない。
`refs/map-station-names.txt` の生成時に NFC 正規化を掛けて解決した。
一方 麴町（U+9EB4）と 麹町（U+9EB9）は別字なので正規化では吸収されない。

### 路線記号は駅ナンバリングがある路線だけが持つ（デバッグで修正）

駅ナンバリングが無い路線（総武本線・内房線・新幹線など34路線）に、
仮の路線記号として "JR" を入れていた。これには2つ問題があった。

1. **実在しない記号をデータが主張していた。** 内房線に「JR」という路線記号は無い
2. **アプリで全駅が同じ「JR」バッジになり、情報になっていなかった**

`symbol` を任意項目にし、駅ナンバリングを持たない路線からは外した。
validate.mjs は「駅番号があるのに記号が無い」をエラー、
「駅番号が無いのに記号がある」を警告として検出する。
アプリ側は記号が無い路線を**路線カラーの丸**で描く。

### デバッグで見つけて直した不具合

- **駅詳細の「つぎのえき」に `undefined` が出ていた。**
  駅番号を持たない路線で `next.numbering + " " + 駅名` を組み立てていたため。
  番号があるときだけ前置するようにした
- **半角カタカナで検索できなかった。**（`ｼﾌﾞﾔ` が0件）
  検索語の正規化に NFKC を入れ、あわせて中黒（・）も無視するようにした。
  これで「万座」で 万座・鹿沢口 が引ける
- **座標検査が同名の別駅を拾っていた。**
  大糸線の有明にゆりかもめの有明（東京）の座標を当てて1075ptの異常値を出していた。
  前後どちらから見ても桁違いに遠い点は別駅の座標とみなして無視するようにした。
  この問題は御殿場線の足柄（小田急と同名）と磐越東線の江田（東急と同名）でも
  実際にデータを歪めており、両方とも駅idを地域で修飾して修正した

### tools/audit.mjs を追加した

validate.mjs は「壊れていないか」しか見ない。
「壊れてはいないが、たぶん間違っている」を探す道具を分けて作った。
統合し忘れの駅、駅番号の並びの乱れ、二重登録の路線などを検出する。

### 駅名＋ふりがなの一致だけで駅を同一視しない（2026-09-02）

駅マスタに登録するとき「駅名とふりがなが一致したら同じ駅」として既存 id を
使い回していた。この処理のせいで、**遠く離れた無関係の同名駅が1駅に結合**された。
2026-09-02 の総点検で10駅（赤坂・中野・平和台・栄町・井野・永田・江田・足柄・
有明・大和）が該当し、たとえば「わたらせ渓谷線の中野駅」を開くと隣が
高円寺・東中野と出る状態だった。

同名の別駅は id を地域で修飾して分ける（`nakano-tokyo` ／ `nakano-gunma`）。
判断は「駅名と読みが同じか」ではなく **「地図の上で同じ場所か」**。

この誤りは validate.mjs では検出できない（データとしては壊れていないため）。
audit.mjs に **「2つの事業者が1駅だけで接している箇所」を洗い出す検査**を足した。
本物の接続駅（五井＝内房線と小湊鐵道 など）も出るので、
確認済み59件を `REVIEWED_JUNCTIONS` に控え、そこに無いものだけを警告する。

### 事業者名は現在の運営会社を書く（2026-09-02）

富士急行線の事業者を「富士急行」としていたが、鉄道事業は
2022年4月1日の吸収分割で **富士山麓電気鉄道** に承継されている。
`name` は現在の運営会社に直し、`shortName` は案内名の「富士急行」を残した。
路線の `formalName` も通称の「富士急行線」ではなく正式名の
「大月線・河口湖線」に直した。

### validate.mjs の出力は必ず全文を読む（2026-09-02）

`node tools/validate.mjs | head -5` のように出力を切って確認していた時期があり、
エラー欄が隠れて**全角数字とカタカナ混じりのふりがなを数バッチ見逃した**。
件数だけ見て「エラー0」と判断しないこと。

### 駅名が違っても、歩いて乗り換えられる駅はつなぐ（2026-09-17）

上野⇔京成上野、町屋⇔町屋駅前のように、名前は違うが通路でつながっている・目の前にある駅を
`data/transfers.json` で結び、アプリの駅詳細に「あるいて のりかえ」として出す。
路線画面の乗換マークでは、同じ駅の乗換（実線の丸）と区別するため**点線の丸**で出す。

**候補の集めかた**（名前の規則だけでは、秋葉原⇔岩本町のような組を見つけられないため）

1. Wikipediaの路線記事の駅一覧から「公式の乗換駅指定」「地下通路で連絡」を抜き出す（東京メトロ・都営15路線）
2. 事業者名や「駅前」を外すと一致する組（京成上野⇔上野 など）
3. Wikipediaで1つの駅記事にまとめられている組（町屋駅前停留場は町屋駅の記事に含まれる など）
4. 全駅の座標を取り、距離が近い組を機械的に拾う

**採否の基準**（利用者の判断）

- 450m以内、または同じ駅施設 → 採用
- 450〜700m → 通路でつながっている・公式の乗換駅指定のものだけ採用
- 700m超 → 見送り（蒲田⇔京急蒲田 721m、練馬⇔東武練馬 3.5km など）
- 距離だけで拾った組は300m以内を採用
- 参考サイト「首都圏のちか駅」（<http://www1.ttcn.ne.jp/tocky/closestation.htm>）と突き合わせ、
  - Level2（公式の乗換駅）・Level3（乗換可能とされる駅）はすべて採用
  - Level1（両駅を同じ場所から目で見られる）は450m以内を採用。450m超の18組は見送り
  - 「惜しい！編」は、パンフレットで乗換駅扱いの桐生球場前⇔運動公園だけ採用（白山⇔本駒込は見送り）
  - サイトに載っていない300〜450mの候補13組は見送り（江ノ島⇔片瀬江ノ島など）
- サイトに無くても残した組：事業者名が付くだけの組（上野⇔京成上野など）と都電の組は、
  サイトが対象外と明記しているため。西武新宿⇔新宿／新宿西口／新宿三丁目と東銀座⇔有楽町は
  Wikipediaの公式乗換・通路連絡の記載を根拠に残した

結果は120組（1つの駅施設11・通路7・公式40・近接62）。

名前が似ていても**まったく別の場所の組が多い**ので、名前だけで結んではいけない。
例：赤塚（水戸市）⇔地下鉄赤塚（板橋区）は97km、京成中山（船橋市）⇔中山（横浜市）は43km。

**距離の注意**：Wikipedia記事の代表地点どうしの直線距離なので、新宿や東京のような大きな駅では
100〜200mずれる。都心は地下鉄駅が密集しているため、400m以内でも乗換に使われない組（上野広小路⇔湯島など）が
大量にある。**距離だけで採否を決めず、つながり方の根拠と合わせて判断する。**

## 未決のまま残していること

着手時に決める。今は決め打ちしない。

- 麹町／麴町、市ケ谷／市ヶ谷 のように事業者と路線図で字体が違う駅を、UIでどう出すか
- 大江戸線の環状部の接続（都庁前〜新宿西口）をデータに持たせるか、UI側で補うか
- 臨時駅の扱い（偕楽園・鹿島サッカースタジアム）。`(臨)` を駅名に含めるか、フラグで持つか
- 分岐線の記号を UI でどう出すか（東京メトロ公式 `m` か、路線図凡例 `Mb` か）
- 新幹線を路線として持つか。持つ場合の駅の粒度
- 「東海道本線・京浜東北線」のような複合ラベルを、路線として分けるか
- 同じ駅名で別の駅（船橋／京成船橋、赤坂など）が全域に広がったときのid修飾ルール
